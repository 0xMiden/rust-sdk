# Harden account state transitions and guarantee post-sync state convergence

Accounts have an implicit state machine where notes have an explicit one: `AccountStatus::{New, Tracked, Locked}` is derived on read from scattered columns (`account_seed` presence + `locked` flag), and transitions happen as side effects of row rewrites spread across `replace_account_header`, `lock_account_on_unexpected_commitment`, `insert_new_account_header`, and `undo_account_state` — e.g. *unlocking* an account is an undocumented consequence of `replace_account_header` defaulting `locked = false`. Separately, sync's account-state resolution is not self-validating: the `PublicAccountUpdate::Patch` path applies node-fetched deltas onto the stored state guarded only by a nonce comparison — there is no check that the patch basis matches the stored state, and no verification that the final stored state hashes to the node-reported account commitment. When the on-chain account has advanced through transactions the local client never saw (a second client, network transactions), we rely on the delta happening to compose correctly; divergence would be silent.

## Motivation

- Account state is where funds live: a divergent stored state means transactions built on wrong inputs, false locks on healthy accounts, or a wallet that silently disagrees with the chain about balances.
- Because the status machine exists only as emergent column effects, every new writer (a sync variant, batch apply, NTL import) must re-discover the invariants by reading four scattered functions — regression risk compounds with every store change.
- This isn't hypothetical: the faucet incident was two writers on one account leaving a store frozen at nonce 114,947 while the chain advanced past 118k.
- Multi-client and multi-device usage make "the chain advanced through transactions this client never saw" the normal case for mainnet, not an edge case.

## State machine

Reinterpreted to match the codebase's existing idiom: accounts get what transactions and notes already have. `TransactionUpdateTracker` owns transaction status transitions during sync and input notes carry state objects with validated transitions — accounts are the only entity whose sync updates travel as a dumb bag (`AccountUpdates`) and whose status decisions happen as implicit row effects at apply time. rust-sdk#2340 already moved `AccountUpdates` next to the tracker and gave it `push_*` methods; this finishes the thought.

- **`AccountUpdateTracker` owns the whole machine**: `AccountUpdates` evolves into a tracker mirroring `TransactionUpdateTracker` — it accumulates per-account events (state advanced via Full/Patch, verified mismatch, superseded, insert/re-import), applies the (status × event) rules (New→Tracked on first state advance, →Locked on verified mismatch absent from history, Locked→Tracked only via verified re-import, rollback only via discard-undo; `StateAdvanced` on Locked is illegal so unlock can't happen by accident), and records typed outcomes (`LockApplied` / `StaleMismatchIgnored` / `AlreadyLocked`). `SyncSummary` reads outcomes from the tracker, deleting #2340's post-apply read-back at the source; `StateSyncUpdate` coordinates it with `TransactionUpdateTracker` for basis-overwrite resolution (it already does this for superseded states). It lives in rust-client, above the `Store` trait, so both store backends (sqlite, web-sdk IndexedDB) sit below the same machine. A pure transition table may exist as a private helper inside the tracker module for exhaustive testing — implementation detail, not API.
- **Enforcement by construction**: non-sync writers (`add_account`, `apply_transaction`) build their account updates through a tracker instance too, and the store's account-mutation methods accept only tracker-built update values (carrying basis and outcome) — no store API takes a raw header, so "all writes to `locked`/`account_seed` go through the machine" is the type system, not a convention.
- **Store keeps enforcement, not policy**: the CAS basis check inside the SQL transaction, the insert-conflict fix, `CHECK` constraints, and the mechanical row effects (archive/replace/lock stamping). The split is load-bearing: an in-memory tracker can't defend against a second process on the same database file — the tracker decides, the store re-validates under CAS.
- The lock decision's stale-data guard ("is this commitment in `historical_account_headers`") needs store history the tracker doesn't have: the client reads the predicate before building the update (one `EXISTS` per mismatched account — rare), the tracker decides, and the store re-checks the same predicate inside the apply transaction, erroring on divergence instead of silently deciding differently.
- Non-sync writers (`add_account` insert/re-import, `apply_transaction`, `undo_account_state`) call the transition core directly — the tracker is sync's accumulator, not a universal gate; the "all writes to `locked`/`account_seed` go through one place" invariant attaches to the core plus the store mechanics.
- Replace stringly transition failures (`StoreError::DatabaseError(...)` for nonce violations) with typed errors (`StaleAccountState { expected, actual }`-style). The nonce-guard asymmetry (`update_account_state` allows equality, `apply_sync_account_patch` requires strictly greater) dissolves rather than getting documented: `StateAdvanced` requires a basis-commitment match, which subsumes the nonce checks; equal-nonce full replacement is legal only via `ReImported`, where network verification substitutes for the CAS.
- Fix `insert_account` silently overwriting an existing header (including its `watched` flag) with no historical row — fail on conflict at the store; the client's explicit `overwrite = true` path routes through `ReImported`.
- Optional hardening, not a prerequisite — anchor public/watched imports at the client's sync height H (`GetAccountRequest.at` supports it; imports currently fetch at chain tip): the fetched proof then verifies against a header the client already trusts, and the store stays a uniform snapshot at H. Import-at-tip remains safe once this issue lands — a moved account's first sync fails the basis check and self-heals via full fetch (one wasted round trip, no corruption) — but note that *without* the refactor, first-sync-after-import can double-apply non-idempotent vault deltas onto a tip-fetched basis with only the nonce guard watching. Private state files keep tip verification: it rejects a stale file at import instead of importing it and locking on the next sync.
- Add `CHECK` constraints so illegal column combinations (e.g. `nonce > 0 AND account_seed IS NOT NULL`) can't persist — rides WORK-02's pre-freeze migration.

## Sync convergence

Two invariants: **(1) after every sync, a public account's stored latest state equals the on-chain state at the sync height, regardless of which transactions the client knows about; (2) pending local transactions are adjudicated on evidence — timeouts decide when to adjudicate, never the verdict.** A transaction whose effects are part of the on-chain state must end `Committed` even if its inclusion record was never delivered. Expiration is itself evidence when sync has covered blocks contiguously through the expiration height (the record would have been seen), so the common path needs nothing new; at state jumps (self-heal, offline gaps) expiry/staleness triggers the evidence check instead of concluding it. When evidence is genuinely unobtainable, a last-resort timeout discard remains — under a distinct cause (`Discarded(Unresolved)`-style) so callers can distinguish "provably failed, safe to retry" from "gave up waiting, don't re-send funds".

- Basis check: `apply_sync_account_patch` must verify the patch was built against the currently stored state (commitment compare, not just nonce), returning a typed conflict error otherwise. (Generalized to all store mutations by WORK-09.)
- Post-apply verification: after applying a `Full` or `Patch` update, recompute the account commitment from what was actually stored (header + SMT forest roots) and compare against the node-reported commitment — fail the sync transaction on mismatch instead of persisting divergence. (`apply_account_patch` currently trusts `final_account_state`'s roots rather than recomputing from what it wrote.)
- Recovery path: on basis mismatch or verification failure, fall back to fetching the full account state from the node (self-heal) rather than erroring the whole sync; any pending transactions whose basis the fetch overwrites are resolved per the rules below, in the same store transaction.
- Same CAS discipline on `apply_transaction` so two writers on one account produce a typed conflict instead of silent interleaving (see the faucet incident: store frozen at a stale nonce with two writers).
- Basis-overwrite resolution: whenever sync overwrites an account state that a pending local transaction used as its basis — same-nonce race, a `Patch`/`Full` apply advancing past it, or a self-heal fetch — that transaction is resolved (committed or discarded, never left dangling) in the same store transaction as the overwrite. Today only the same-nonce case routes through an explicit discard (rust-sdk#2340's `superseded_local_states`); the patch and self-heal paths leave the transaction to the timeout fallbacks.
- `TransactionUpdateTracker` fixes that ride along: (a) it is order-dependent today — `apply_input_note_nullified` discards any pending tx consuming that nullifier, and only the fact that inclusions are processed first stops it from discarding the client's *own committed* tx (a nullifier spent by your own tx is proof of commit, not failure); make the tracker two-phase — accumulate evidence during sync, adjudicate once in a `finalize()` — so ordering stops being load-bearing. (b) The unauthenticated-note fallback match uses `account_id + init_account_state` only and can commit the wrong tx when two pending txs share a basis; require the final commitment too. Keep what's right: guarded finality and the discard cascade via `apply_invalid_initial_account_state`.
- Evidence-based status resolution: `Committed` is currently only ever set when the node's sync response happens to contain the transaction's inclusion record (`apply_transaction_inclusion`), while `apply_sync_height_update` discards on timeouts (`DiscardCause::Stale`, `DiscardCause::Expired`) — so a transaction that committed on-chain but whose record the client never received (offline past the node's retention window, a self-heal state jump) ends up `Discarded`, indistinguishable from one that genuinely failed. Rules: a pending transaction whose `final_account_state` lies on the chain's state path (e.g. it equals the basis a sync patch was built on) is proven `Committed` without a record; `Discarded` requires positive evidence (same-nonce loss, consumed input note, expiration height passed with the state provably not included); the ambiguous remainder (state jumped past it via full fetch) gets a targeted per-transaction node query — cheap, since pending local transactions number a handful, unlike stepping through the account's full on-chain history (the faucet has 100k+ txs). May need a node-side transaction-status endpoint; note it as an upstream ask if so.

- Open question — store foreign transaction records? `apply_transaction_inclusion`'s no-match branch holds the full record and discards it after extracting nullifier attributions. Persisting the headers (tx id, account, block, initial/final commitment, nullifiers, output note ids; born `Committed`, outside the pending machinery; Native accounts only — a watched faucet would drag 100k+ rows) would give multi-device history ("what changed my balance") and make the chain's state path explicit locally, reducing node queries for pending-tx resolution. Against: none of the invariants need it (the node-query fallback covers evidence), it's best-effort by construction (state jumps leave holes), and it's a product decision about what the transactions table *means*. Not on this issue's critical path — a brand-new table is a cheap forward migration even post-freeze once WORK-02 lands, so this can be decided with wallet/product input later.

A natural implementation vehicle (shared with WORK-09): restructure `StateSyncUpdate` as a guarded changeset — plain upserts only for append-only/content-addressed data (headers, MMR nodes, scripts), `{basis, final}` CAS entries for account/note/transaction state, and post-write commitment verification where a node commitment exists. That turns the basis-overwrite rule into a construction-time obligation (the changeset builder must carry a resolution for every pending transaction touching an account in the set) instead of a runtime discipline, and makes re-applying a changeset after a crash idempotent.

## Relationship to rust-sdk#2340

Supersedes rust-sdk#2340 (closed in favor of this issue); its semantics carry forward unchanged — a mismatch resolving to a commitment already in local history is stale data and must not lock or be reported; already-locked accounts aren't re-reported; same-nonce-superseded local states get their transactions discarded. The PR's mechanism (reading lock status back from the store around the apply, `locked_accounts_among`) existed only because store transitions don't report outcomes; here the tracker's typed outcomes carry the same information at the source. Its store test (`lock_account_ignores_commitment_present_in_history`) becomes a cell in the transition matrix, and its branch (`igamigo-fix-acc-update`) — the `AccountUpdates` unification and superseded-state machinery — is the starting point for the tracker PR. Note: until the tracker PR lands, `SyncSummary::locked_accounts` keeps over-reporting; if a release ships in between, reconsider landing the PR's narrow fix first.

## Testing

One layer per seam of the architecture; no layer needs the harness of the one above it.

1. **Transition core — exhaustive, not sampled.** Statuses and events are finite enums, so enumerate the full (status × event) matrix programmatically and assert every cell's outcome (including the watched-flag and stale-mismatch variants as event parameters). A new event variant fails the coverage assertion until its cells are defined. Pure function: no store, no async. rust-sdk#2340's `lock_account_ignores_commitment_present_in_history` becomes one cell.
2. **Tracker — property-based over event sequences.** Feed `AccountUpdateTracker` random event streams (no chain, no DB): every outcome agrees with the core; every basis-overwrite has a matching transaction resolution recorded before the update is handed to the store; re-applying the same events is idempotent; summary counts are derivable from outcomes alone.
3. **Store enforcement — conflict and atomicity tests.** For each mutation with a basis: derive the update, mutate the stored state, apply — assert the typed conflict *and* a byte-identical store (dump-compare, not spot fields). Two-writer test reproducing the faucet shape: two store handles interleaving `apply_transaction` / `apply_state_sync` on one account — one wins, the other gets a typed conflict, never silent interleaving. Forest/SQL atomicity: force a failure mid-apply and assert the in-memory SMT forest rolled back with the SQL transaction (`with_forest_snapshot` is the seam).
4. **Convergence — randomized end-to-end against `MockChain`.** No hand-written chain model: `MockRpcApi` already wraps a real `MockChain` (real commitments, real MMR, per-block history), so the reference model is the chain itself. Drive a full in-process client with seeded random action sequences {local tx, foreign tx applied directly to the `MockChain`, sync, discard, re-import, skipped syncs to simulate offline}; after every sync assert (a) stored latest state == `MockChain` account state at the sync height, (b) every pending transaction is resolved per the evidence rules — the script knows ground truth, so a committed-but-unobserved transaction ending timeout-`Discarded` is a failure, (c) the private-account variant locks exactly when it should. The interleavings are the point — foreign transactions and offline gaps produce the sequences nobody hand-writes.
