# Improve FPI flows: limits awareness, chunking, parallel prefetch, watch-account integration, docs

Teams running FPI-heavy workloads (N trades per transaction, each reading several foreign storage maps) hit the node's undocumented 64-`storage_map_key` limit as an opaque `OutOfRange` gRPC error, and pay avoidable latency on every transaction: foreign-account inputs are fetched sequentially (`retrieve_foreign_account_inputs` awaits one account at a time), oversized `AccountStorageRequirements` are sent as a single doomed request instead of being split, and any storage key not declared upfront triggers a blocking per-key network call during execution. Watch accounts — which keep foreign-account state locally, updated on every sync, eliminating those round trips — already solve most of this, but are effectively undiscoverable ("Wasn't aware of the watch accounts" — from a team actively fighting the problem).

## Motivation

- FPI is the client's only mechanism for reading shared on-chain state inside a transaction — its latency and limits are the latency and limits of every DeFi-shaped app on Miden. Real integrators (pool→vault trading) are hitting the 64-key ceiling today and working around it by manually sharding accounts.
- Every undeclared storage key costs a blocking network round trip *mid-VM-execution*; every foreign account costs a serial round trip before execution starts. For an N-trades-per-transaction workload this is the dominant cost, and all of it is avoidable client-side.
- The node's limits exist deliberately (memory pressure per FPI-loaded account); the client's job is to compose within them — chunking, caching, watch accounts — not to make users discover them via opaque `OutOfRange` errors.

## Client work

- **Limits (verified 2026-07-23 — no node coordination needed):** the node already emits the `GetAccount` limits via `GetLimits` — `storage_map_key = 64` *and* `storage_maps` (per-request slot cap bounding `all-entries` requests) — in 0.15.1 and 0.16-alpha alike; the proto is a generic `map<endpoint, map<param, limit>>`. The client's `TryFrom<proto::RpcLimits>` (`rpc/domain/limits.rs`) extracts four known params and silently discards the `GetAccount` entry. Work is purely client-side: add both fields to `RpcLimits` and drive chunking from them. Treat them as optional-with-default on parse (the converter currently hard-errors on missing params — additive limits from newer nodes must never break `GetLimits`). Still gated on WORK-01: `RpcLimits` is a public-field struct, so gaining fields is breaking today.
- **Chunking:** when `AccountStorageRequirements` exceeds the limit, transparently split into multiple `GetAccount` requests and merge the resulting storage-map entries — safe because all chunks pin the same `AccountStateAt::Block`.
- **Parallelism:** fetch inputs for multiple foreign accounts concurrently instead of the current sequential loop.
- **Witness/proof cache:** cache `AccountProof`/witnesses keyed `(account_id, block_ref)`, invalidated when sync height advances. Two FPI transactions in the same sync window against the same foreign account currently fetch the identical proof twice. Only spends a round trip when a transaction actually needs a witness; amortizes across every transaction in the window — only the first transaction per window pays latency.
- **Local-first assembly for watched accounts (partially exists — verified 2026-07-23):** code is already local-first (`with_known_code` skips re-download) and vault re-transfer is already avoided for tracked accounts (`VaultFetch::IfChangedFrom`). The gap is storage maps: `fetch_public_account_inputs` always sends `StorageMapFetch::Slots(storage_requirements)` to the node and never consults the `watched` flag (its only use in the tx path is the "can't execute as watched" guard). For a watched account the full maps are local and current as of sync height — exactly the block FPI anchors to — so **no storage requirements are needed at all**: build `PartialStorageMap::new_full` from the local maps (the same shape the `AllEntries` network path produces), consuming zero of the node's 64-key budget; only the account witness comes from the network. Fall back to the network path for non-watched accounts. Pre-implementation check: trace where vault assets come from when the node reports the vault unchanged (`IfChangedFrom` matches) — the response-to-inputs conversion appears to read assets only from the response.
- **Vault requirements (gap verified 2026-07-23 — needs node support):** there is no vault analogue of `AccountStorageRequirements` at any layer. `ForeignAccount::Public` declares storage only; the `GetAccount` proto gives storage per-slot/per-key selectivity but the vault only a binary `asset_vault_commitment` (full list if changed); the response carries no per-asset proofs; and oversize vaults fall back to `SyncAccountVault` **from genesis** even when the transaction reads one asset. Propose `AccountVaultRequirements` (vault keys → selected assets with SMT proofs, mirroring the storage shape — the vault is an SMT and `AssetWitness` already exists as a type) as a node ask alongside the witness proposal. Interim: watched accounts sidestep this too — the local forest can produce `AssetWitness` with no network (the local-first item above covers vault as well as storage).
- **Error UX:** map the node's `OutOfRange` limit rejection to a typed error with an `ErrorHint` naming the limit and the mitigations (declare requirements upfront, chunking, watch accounts, sharding).
- **Docs:** an FPI guide covering the data-resolution order (execution cache → local store → network), prefetch vs. lazy trade-offs, and — explicitly distinguished, since users conflate them — the protocol kernel's 63-foreign-account limit vs. the node's per-request 64-key limit; watch accounts as the scaling strategy.

## Node-side proposal (September conversation)

- **Opt-in `include_account_witnesses` on `SyncTransactions`** — request already carries `repeated account_ids`, so the node knows which accounts; add `bool include_account_witnesses` to the request and `repeated AccountWitness account_witnesses` to the response. Witnesses ride the **final page only** (anchored at the end block the client adopts as sync height); anchoring fits the ≤30-blocks-of-tip constraint the node already documents for `SyncAccountVault`.
- **Cost:** ~0.7–1 KB per watched account per sync (`AccountWitness` = two IDs + commitment + `SparseMerklePath` carrying ~log₂(N) non-empty siblings). Total bytes ≈ identical to the `GetAccount` alternative; what piggybacking saves is W round trips and W rate-limit slots per sync.
- **Fallback design if coupling to `SyncTransactions` is disliked:** a batched `GetAccountWitnesses(account_ids, block_num)` endpoint — still one extra round trip, but collapses W `GetAccount` calls into one.
- A standalone per-sync `get_account` prefetch loop on the client was considered and **dropped**: same treadmill cost as sync-delivered witnesses plus N extra round trips against node rate limits — dominated by the cache (item above) now and by sync-piggybacking later. The client cache is fill-mechanism-agnostic: when the node field lands, it gets populated from the sync response instead of on-demand fetches.
