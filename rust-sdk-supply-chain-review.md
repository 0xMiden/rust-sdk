**rust-sdk supply-chain review**

No evidence of the reported Cursor Claude Code extension payload was found in the reviewed source changes. Four independent code issues deserve correction. This is a static source review and indicator search, not a certification that the repository, contributors, or release artifacts are uncompromised.

The review covers the 23 open PRs and 72 merged PRs listed in the pinned inventory. It includes the new #2774 PR and the refreshed revisions to #2735, #2749, #2762, #2763, #2764, #2767, and #2768. Both `main` and `next` remained unchanged between the two audit snapshots.

**Incident and review boundary.** Cursor identifies malicious `anthropic.claude-code` versions 2.1.312 and 2.1.313 distributed through its marketplace. The payload attempted SSH access and persistence. See [Cursor's incident notice](https://cursor.com/blog/claude-code-extension-security-notice). Microsoft states that its Visual Studio Marketplace and the npm package were not affected by this incident. See [Microsoft's analysis](https://www.microsoft.com/en-us/security/blog/2026/10/30/inside-malicious-claude-code-branded-cursor-extension-persistent-ssh-backdoor/).

The relevant repository risk is that a compromised developer workstation could modify code, dependencies, or release workflows. The original malware need not appear verbatim in a malicious PR. This review therefore checks both the published indicators and security-sensitive changes without those indicators.

**Findings.** These are static findings, with no exploit execution. Their recorded history predates the disclosed incident. No evidence links them to that incident. Priority describes the proposed engineering response, not attribution or a formal CVSS score.

**#2595: validate the funding note before signing.** At [funding/mod.rs:174](https://github.com/0xMiden/rust-sdk/blob/56db3b59fc0bc05ab3cd6e108c1c0f63c74ebf9a/crates/rust-client/src/funding/mod.rs#L174), `fund_account` accepts the HTTP receipt's note ID when its stored record is committed. At [line 191](https://github.com/0xMiden/rust-sdk/blob/56db3b59fc0bc05ab3cd6e108c1c0f63c74ebf9a/crates/rust-client/src/funding/mod.rs#L191), it builds a consume request and submits it. There is no intervening check that the note is a supported P2ID payment to the requested account with the requested native asset and amount. Checking the faucet's advertised account ID does not authenticate the contents of the returned note.

A malicious or compromised configured faucet can select a real committed note that the wallet discovers. A spending note, including a standard SWAP note, can move assets from the consumer's vault. The usual filesystem signer signs the resulting transaction; the helper supplies no funding-specific output restrictions. A valid chain inclusion proof does not establish that the note satisfies the user's funding intent. This requires the funding feature, an attacker-controlled faucet response, a discoverable valid spending note, and a signer that does not independently reject its effects. It is not a proof-forgery attack or evidence of a compromised faucet in production.

Require a canonical supported P2ID script, the intended target, expected native asset and amount, and the documented type/sender policy before calling the signer. Add a regression in which the receipt selects a committed spending note and require rejection before the signing callback.

**#2742: cap note-transport work independently of the service.** The merged change removes the previous 32-page cap. At [note_transport/mod.rs:429](https://github.com/0xMiden/rust-sdk/blob/96c039c8837620fc917f2a21e127012efaf3f9b1/crates/rust-client/src/note_transport/mod.rs#L429), each validated page extends a shared vector and the loop continues while the response says more pages exist. `sync_to` is supplied by the service. It is not a trusted chain height or a client resource limit.

A compromised configured transport can choose a huge fixed sequence bound, return the same valid note with a requested tag on each page, and advance its sequence each time. These pages satisfy the shown validation. The client accumulates the notes before local filtering and import. Individual RPC timeouts do not help when each page returns promptly. Full sync waits for the transport fetch, so chain-update application is also delayed. This is a remote availability/resource-exhaustion issue involving a configured service, not arbitrary inbound network access.

Set a client-controlled page/byte/time budget before accumulation. Preserve progress so a budget stop does not advance the shared cursor past undelivered notes or tags. Test repeated valid notes with a huge service-selected bound. The defect is present at the reviewed `next` commit; no fix was applied in this audit.

**#2598: do not silently retain misnamed plaintext files.** At [encrypted_fs_keystore.rs:251](https://github.com/0xMiden/rust-sdk/blob/14959966bb345b07599f37f696731a48531779a4/crates/rust-client/src/keystore/encrypted_fs_keystore.rs#L251), migration enumerates a filename commitment, reads its contents, and passes a parsed key to `store_key`. That method [derives its destination from the key itself](https://github.com/0xMiden/rust-sdk/blob/14959966bb345b07599f37f696731a48531779a4/crates/rust-client/src/keystore/encrypted_fs_keystore.rs#L297). If the original filename is a different valid commitment, the encrypted copy goes to another path while the original remains plaintext. The returned unreadable-file list does not report the mismatch.

This requires a malformed or misnamed preexisting key file. It does not give an outsider new access to a healthy keystore. It violates the migration's promise to encrypt each readable key or report what remains. Reject/report mismatches before conversion and test that a successful conversion leaves no source plaintext behind. The cipher, random nonces, commitment-bound AAD, and atomic file-writing paths examined did not show a deliberate cryptographic backdoor.

**#2720: remove the local dependency substitution.** [Cargo.toml:114](https://github.com/0xMiden/rust-sdk/blob/ef6efe3454b7cb8f49a78f52ecd9c966c1cf0c5c/Cargo.toml#L114) adds a crates.io override for `miden-protocol` pointing at `../protocol-0.17/crates/miden-protocol`. A clean checkout cannot resolve that directory. A developer who has it builds its current contents, which are outside this PR and unpinned. The corresponding protocol and build-utils lock entries lose registry source/checksum identity. The comment explicitly marks the override temporary. Use a published dependency or a reviewed immutable revision before merging. The override alone does not prove malicious source content.

**What was checked.** Every PR received file-list triage and automated inspection of complete Git diffs. Manual review concentrated on process execution, credential handling, signature and proof checks, state trust boundaries, RPC destinations, dependencies, CI, build scripts, editor/agent configuration, and new binary material. Large mechanical and repeated release-sync changes were not all independently verified for functional correctness.

Open PR diffs use the recorded base/head merge base. Merged PR diffs use the actual landed merge commit against its first parent. This avoids relying only on potentially truncated API patches. The separate commit scan covers reachable `main`/`next` history and available open-PR commits within the selected audit window, including intermediate changes that may not survive in a final PR diff. It does not recover deleted or unreachable force-push history.

Published network, SSH-key, persistence, and payload-hash indicators were checked against the diffs and every repository blob in `main`, `next`, and the open heads. Searches also covered suspicious execution and download patterns, credentials, verification bypasses, encoded payloads, and Unicode format-control characters. Broad-pattern matches were inspected in context. Existing submodule contents were not recursively audited.

All 34 lockfile-changing PRs in the refreshed inventory were compared structurally using complete Git blobs. None changed the checksum of an existing package with the same name, version, and source. Merged comparisons use actual landed commits. Apart from #2720, source changes examined used the usual registry or explicit upstream Miden Git pins. Checksum consistency does not establish that upstream packages are trustworthy.

CI changes examined did not introduce privileged PR execution, secret uploads, new arbitrary remote shell loaders, or disabled TLS verification. The new binary storage-key fixture matches the upstream node development fixture. The suspicious-looking CA advisory hostname appears in explanatory comments, not an executed download. No changed editor/agent startup hooks were identified.

The refreshed RPC wrapper-removal review confirms that the built-in transport still calls the per-method validators. Account identity, requested block, note membership, and proof-decoding checks remain in the examined paths. Custom `NodeRpcClient` implementations must enforce their own response checks. The new #2774 dispatch still uses the validating call path; only V1 exists, so this revision cannot downgrade to an older API. The #2749 serialization review checks required fields, unknown enums, store decoding, and ChainAnchor reconstruction. No additional actionable security issue or attack-linked behavior was identified in those refreshed paths. These are targeted security conclusions, not full wire-compatibility or migration-correctness approvals.

**Limits and next actions.** This review did not execute PR code, install dependencies, run builds/tests, or run incident-remediation scripts. The findings are supported by source traces, not end-to-end exploit tests. No source fixes, commits, pushes, issues, or PR comments were made. The existing account-tracker worktree was not changed.

A clean repository scan cannot establish that contributor devices, tokens, SSH keys, organization audit logs, external dependencies, or published artifacts are clean. For contributors who installed an affected extension, follow the incident-response checks in Cursor's notice, preserve evidence, and assess credentials from a trusted machine. That endpoint investigation remains separate from this source review. No contributor device was inspected here.

Before merge, address #2595, #2598, and #2720. Address the already-merged #2742 availability regression on supported affected branches. Re-review any new commits after the pinned snapshot. No evidence found here justifies attributing these defects to the extension attack.
